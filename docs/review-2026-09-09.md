# BSN CRM product and code review - 2026-09-09

Review only. Findings below remain open; passing unit tests do not cover all UI flows.

## Critical workflow findings

1. **P1 - Shared record array can open/copy/send the wrong customer.** `src/main.js:616` replaces `state.activeRecords` when a KPI drill-down opens. The underlying appointment rows and copy/Telegram buttons still use their old indices. Browser reproduction: open Lead KPI, Escape, click first appointment; detail matches first Lead instead of the visible appointment. Telegram was not sent during review. Separate table and drill-down record contexts, and resolve actions against stable record identity.
2. **P1 - KPI drill-down freezes its initial dataset.** `src/main.js:584` skips rebinding while the original handler closes over `records`. Browser reproduction: initial month, change to Today, booking KPI reads 0 but drill-down reports 8 records in Today. Store current KPI datasets independently of one-time event registration.

## Data correctness

3. **P2 - Invalid calendar dates silently become valid dates.** `src/core/api/sheets-api.js:98`: mocked Marketing input `31/02/2026` returns `2026-03-03`. Validate calendar components before accepting a row; preserve a quality warning rather than allocating revenue to a different month.
4. **P2 - Upcoming filter drops today's appointments regardless of appointment time.** `src/features/dashboard/ui-helpers.js:77` compares the date at midnight with the current instant and ignores the supplied reference clock. A booking at 15:00 today is excluded by its midnight date. Compare combined appointment date/time; explicitly group unknown times.
5. **P2 - Invalid times pass validation and unknown times become noon for sorting.** `src/features/dashboard/ui-helpers.js:100`: `hasConfirmedTime({time:'99:99'})` returns true. Validate hour/minute bounds and keep unknown times separate from known appointments.
6. **P2 - Multi-service customer filtering loses valid matches.** `src/main.js:353` matches only `customer.service`, selected from the first service in `src/features/dashboard/ui-helpers.js:181`. Synthetic customer with services A and B is not returned by filter B. Filter the complete set of services.
7. **P2 - Missing customer revenue becomes zero.** `src/features/dashboard/ui-helpers.js:158` starts revenue at zero and `Number(null)` remains a finite zero. The table then renders zero as a dash, while copied messages can report zero. Track whether revenue exists separately from its sum.
8. **P2 - Customer detail reads the wrong date field.** `src/main.js:536` reads `aptDate || date`, but derived customers expose `latestDate`. The table can show an interaction date while detail is blank.

## Budget and reports

9. **P2 - Stale fallback ignores a new selected month.** `src/main.js:687` always returns the previous model after refresh failure. Browser reproduction with mocked 503: select August, UI returns September. Cache models by period or recalculate from the retained snapshot with a stale label.
10. **P2 - Budget bars imply positive values for zero/missing data.** `src/features/dashboard/budget-view.js:7` uses a minimum 4 percent bar for zero and null. Browser evidence includes zero-revenue days with 4 percent bars. Use actual zero height and a distinct missing-data indicator; show chart scales.
11. **P2 - Daily drill-down warnings still stringify objects.** `src/features/dashboard/budget-view.js:18` calls `issues.map(esc)` instead of formatting `issue.message`. The separate warning badge fix does not cover this path.
12. **P2 - KPI lists truncate without disclosure.** `src/main.js:607` renders the first 250 rows while the summary reports the full count. Add explicit pagination or a visible limit and complete export.

## UI, accessibility and session

13. **P2 - Dialog keyboard/focus lifecycle incomplete.** `openDetail` hides the parent drill-down and then saves a focused element from that hidden parent. `openDrilldown` does not save its trigger. There is no focus trap, and Enter handling covers table rows but not drill-down rows. Preserve the original visible trigger and implement a shared dialog lifecycle.
14. **P2 - Mobile overflow checks hide clipped content.** Marketing at 375px reports page overflow 0 but main content overflows by 869px. `overflow-x: clip` masks that measurement. Screenshot `output/audit-budget-mobile.png` also shows the export button wrapping into three lines. Check each container and table scroll region, not only the document width.
15. **P2 - Lead has no Telegram action.** `renderLeadRow` uses `renderRowActions`, which renders only Copy. Appointments and Customers have Telegram buttons. The intended per-record sending workflow is incomplete for Leads.
16. **P2 - Filter/session state is only partially persisted.** `saveFilterState` stores period/start/end, but not service, status, source or record tab. URL hashes do not select CRM tabs. This differs from the approved unified filter behavior.

## Security and operational boundaries

- Google client requests the read-only Sheets scope; `/api/sheets` uses source allowlists.
- Production network access checks use configured client and trusted-proxy CIDRs. No production host configuration or proxy routing was verified in this review.
- Telegram token remains server-side. Group override intentionally allows an internal operator to choose a group; no group ownership or user-role isolation exists. This matches a single internal facility, not a multi-tenant product.
- Telegram forwarding was inspected through source/tests, not a live message to customers or staff. Android/iOS phone-link behavior is unverified.
- Last-good snapshots exist in server memory; they do not survive server restart. A fresh process with unavailable Sheets cannot serve the previous snapshot.
- No billing workflow exists; no payment behavior was tested.

## Validation and coverage

- Browser: Overview, CRM tabs, KPI/detail sequence, Marketing, Settings, period selection, mocked refresh failure. No real Telegram message or Sheet write.
- Module reproductions: impossible dates, malformed times, multi-service customer aggregation and missing revenue.
- Previously run 23 tests passed, including server allowlists, stale CRM cache, phone entities and budget arithmetic. They do not cover the reproduced table/KPI context bugs.
- Current code inspection covered parser, UI state/rendering, customer/date helpers, budget calculations/view, API/Telegram routes, cache/retry, Google client, network controls and deployment entrypoints.
- Not established: exhaustive browser/device coverage, production deployment health, live Telegram delivery, measured usability targets, or absence of all security vulnerabilities.
